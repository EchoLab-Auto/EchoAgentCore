# 工程逻辑纪律：先陈述方案，再动第一笔

适用：任何要改动项目的工程任务（写代码、改配置、重构、修 bug、搭项目）。
**不管任务看起来多简单**——实测最长的失控片段（306 步）首条指令只有四个字
「请你进行检查」。

## 为什么需要这条闸门

从 14008 次工具调用 / 6027 条推理记录里量出来的四个数字：

| 现象 | 实测 |
| --- | --- |
| 推理中途推翻自己的判断（「等等 / 哦 / 实际上 / 我搞错了」） | **12.5%** 的推理记录 |
| 推理中途换方案（「换个思路 / 改成 / 放弃 / 改用」） | **7.2%** |
| 同一个文件被反复修改 | 单个文件最高 **57 次** |
| 用户不得不回来纠正方向（「你是不是把它做到 X 里了」「说错了」） | 用户消息里 **8.2%** |

这些��不是模型能力问题，是**动手前没把方案说清楚**：

- 没有验收标准 → 只能靠反复「改一点 → 跑一次」来获取信息（实测 59 个 turn
  里 197 次改-验循环，单 turn 最高 65 次）；
- 没有改动清单 → 改到第三个文件才发现第一个改错了，回头重改，一个文件改 57 次；
- 没有「已确认 / 仍是假设」的分栏 → 把假设当事实用，直到撞墙才推翻，一次推翻
  就废掉前面几十步。

## 一、什么时候必须过闸门

| 触发条件 | 例子 |
| --- | --- |
| **指令本身模糊或极短** | 「开始」「用B吧」「请你检查」「请你进行检查」「继续」「做吧」 |
| **改动跨 ≥2 个文件或 ≥2 个模块** | 改契约 + 改实现 + 改调用方 |
| **跨仓库** | Core + Panel + ui-frame 一起动 |
| **实现路径不确定** | 有 2 种以上合理做法，或不知道哪一层该负责 |
| **不熟悉的代码库 / 半年没碰的模块** | 首次进入的仓库 |
| **探索性任务** | 「优化一下精度」「看下为什么慢」「检查一下有什么问题」 |
| **任何预计 ≥20 次工具调用**的活 | 大改造、迁移、批量替换 |

不需要闸门：一次性的单点查询、明确的单文件小改、用户已给出完整步骤的执行。

## 二、方案陈述的四个必填段

动手前用**一条消息**把这些写出来（写给自己看，不是给用户写汇报）。四段缺一段
就不算过闸，先去补信息。

```text
【目标与验收】
- 要做成什么样：（一句话）
- 怎么算做完：（可执行的验收命令 / 可观察的现象）
- 不做什么：（明确排除项，防止顺手扩张）

【事实与假设】
- 已确认：（事实）← 来源 文件:行号
- 已确认：（事实）← 来源 文件:行号
- 仍是假设：（必须验证的点）+ 打算怎么验证

【改动清单】
| 文件 | 改什么 | 为什么非要改它 |
| --- | --- | --- |
| path/a.rs | 加字段 X | 契约源头 |
| path/b.rs | 读取 X | 唯一的消费方 |

【风险与回退】
- 最可能错的地方：
- 出问题怎么退：（git checkout / 备份路径 / 关闭开关）
- 需要用户确认的点：（有就列，没有就写「无」）
```

### 为什么每一段都在解决问题

| 段 | 治的病 |
| --- | --- |
| 目标与验收 | 「改-验循环」——没有验收标准，测试就变成了探测工具 |
| 事实与假设 | 「12.5% 中途推翻」——把假设显式写出来，才会去验它 |
| 改动清单 | 「57 次改同一文件」——清单逼你一次想清全部受影响点 |
| 风险与回退 | 「用户 8.2% 回来纠正」——目标错时能快速退回，而不是在错的方向上继续加码 |

## 三、什么叫合格的方案（对照）

### 不合格（真实反例，都是「直接开干」）

```text
我来实现一下内嵌形态。
→ 立刻 edit_file
```
缺：内嵌形态有几种？嵌进谁？验收怎么判断「嵌好了」？前 40 步全在猜。

```text
请你进行检查  →  连续 306 步 bash，零方案、零委派、零中间确认
```
缺：检查什么范围、什么算问题、查到什么程度停。

### 合格

```text
【目标与验收】
- 把 panel 的 workspace 卡片改成可折叠。
- 验收：npm run build 通过 + 手动点 3 个卡片确认折叠/展开 + 刷新后状态保持。
- 不做：不改折叠动画曲线，不改其它卡片。

【事实与假设】
- 已确认：卡片状态存在 ChatView.vue 的 `collapsedCards` ref（src/components/ChatView.vue:412）
- 已确认：持久化走 localStorage，键 `panel.collapsed`（src/utils/persist.ts:88）
- 仍是假设：折叠动画复用现有 transition 类 → 待确认 src/styles/motion.css

【改动清单】
| ChatView.vue | 卡片加折叠按钮 + 状态读写 | 唯一的渲染点 |
| persist.ts | 无（复用现有 API） | —— |

【风险与回退】
- 最可能错：状态键与旧版本冲突 → 先读一遍现有键名
- 回退：git checkout -- web/src/components/ChatView.vue
- 待确认：折叠后是否要记住滚动位置？（问用户）
```

## 四、执行中的偏离处理

**规则：一旦出现下面任一信号，立刻停手，先更新方案，再继续。**

| 信号 | 动作 |
| --- | --- |
| 发现前面认定的事实是错的 | 在「事实与假设」里划掉它，重新评估改动清单 |
| 想换实现路径 | 写清「原路径为什么不行 / 新路径为什么行」，再动第一笔新路径 |
| 改动清单要加第 3 个文件 | 说明新文件为什么必须动；说不清就是范围失控 |
| 同一个文件第 3 次修改 | 停：前两次错在哪？是不是前提没查全？ |
| 连续 2 次验证失败 | 不要重跑同一条命令，也不要盲目缩小范围——回去检查方案里的假设 |
| 工具调用累计到 50 步仍未过半 | 做检查点：剩下的活能不能委派 / 能不能拆 |

**禁止的自我欺骗**：在推理里悄悄改主意、只改代码不改方案。方案是给自己的
锚点，偷偷改锚点等于没有锚点。

## 五、验收标准必须先定，且只能验一次

「改一点验一遍」是把验证当探测用——真实代价：59 个 turn 里有 197 次改-验循环，
最高单 turn 65 次验证；其中 62% 的验证没限定到改动的 crate，24.8% 直接
`--workspace`。

规则：

1. **单文件改动不验证**——除非该文件是这个 crate 的唯一入口。
2. **同一 crate 累计 ≥3 处改动，验一次**，且用窄口径（`cargo check -p <crate>`、
   `vitest run <path>`），不要 `--workspace`。
3. **一批活做完，全量验一次**（`cargo test --workspace` / `npm run build`）。
4. **验收失败不重跑同一条命令**：先读错误、定位原因、改一处，再验。
5. 验证的真实身份是**收尾确认**，不是「看看现在什么状态」——要探测状态用
   `git status` / `cargo check`（1~2s）/ 读文件，别用 `cargo test`（8.9s）和
   `clippy`（57.8s）。

## 六、指令模糊时的第一动作：复述目标

用户给的是执行型短指令时（「开始」「用B吧」「请你检查」），**第一动作不是动手，
是复述**：

```text
我理解要做的是：<目标一句话>
范围是：<涉及哪些仓库 / 模块>
验收是：<怎么算做完>
不碰：<排除项>
（如与你的意思不符，先纠正我再开工）
```

这一步成本是一条消息；不做的话，实测要花 306 步才发现方向偏了。

**特别注意过的两个真实错误**：

- 「把它做到 WM-bfm-logo 中了」——目标搞错（该做 A 却做了 B），用户回来纠正。
  复述目标就能拦住。
- 「说错了，是间距有点大」——需求理解偏。先在复述里写出「要解决的具体现象」，
  而不是直接改代码。

## 七、与其它技能的分工

| 技能 | 管什么 | 关系 |
| --- | --- | --- |
| `coding` | 写之前把前提建全（查定义/调用方/依赖/测试/配置） | 本闸门第二段「事实与假设」的执行手段 |
| `long-task-efficiency` | 怎么少花轮次（打包、后台化、不重复读） | 方案定好后，执行阶段的效率 |
| `subagent-delegation` | 什么活派出去 | 方案里「改动清单」跨仓库时，按仓派 |
| **本技能** | **方向对不对**（做什么、怎么算做完、错了怎么退） | 前面三道都建立在「方向正确」上 |

## 八、自检清单

开工前：

1. 这条指令是模糊的执行型短指令吗？（是 → 先复述目标）
2. 四个必填段都写了吗？（目标与验收 / 事实与假设 / 改动清单 / 风险与回退）
3. 验收标准是可执行命令或可观察现象吗？（不是 → 还没想清）
4. 改动清单里每个文件都能说清「为什么非要改它」吗？
5. 「仍是假设」那几项打算怎么验证？验证成本多少？
6. 有没有先查前提（`coding` 的五问）再开第一笔？

执行中：

7. 有没有出现「等等 / 实际上 / 我搞错了 / 换个思路」？（有 → 先更新方案再继续）
8. 改动清单外的文件被动到了吗？（动了 → 为什么，说得清吗）
9. 同一个文件改到第 3 次了吗？（是 → 回查前提，不是继续改）
10. 连续 2 次验证失败了吗？（是 → 回查假设，别重跑）
11. 步数过 50 了吗？（过了 → 该不该委派 / 该不该拆）
