# 后台任务与并行分支

## 目标

模型推理和工具调用不能持续占用共享会话的 `turn_lock`，否则 TUI、QQ 私聊和群聊
都会互相等待。所有普通轮次都会使用创建时的历史快照在临时分支中执行；主会话只在
登记输入、获取快照和合并结果时短暂持锁。后台任务接受后立即返回 `task_id`，同样
使用创建时的历史快照独立运行。

普通回复分支全局最多同时执行 8 个。更多分支保持排队和可取消状态，不占用主会话锁。

## 生命周期

```text
主会话收到请求
  -> spawn_background_task / spawn_parallel_task
  -> 保存共享历史快照、创建 task_sequence
  -> 立即向当前对话返回 task_id
  -> 1..8 个临时分支并发运行
  -> 完成事件进入 OrderedCompletionBuffer
  -> 按 task_sequence 写入共享上下文
  -> 主 Agent 显式投递到每个声明目标
```

同步 `run_subagent` 仍用于短推理。后台分支可调用普通工具，但消息发送、文件上传、
适配器启停和框架更新不向分支开放。分支不能直接影响聊天目标。

## QQ 并发回复

QQ hook 只负责完成门控、登记消息和启动处理，不再等待整个 Agent 轮次结束。每条通过
gate 的 QQ 消息会在主锁内写入共享历史并保存当时的历史快照，随后立即释放主锁并
创建一个可取消的临时回复分支：

- 每条消息始终进入独立分支，不存在持有主锁执行模型或工具的“前台轮次”。
- 每个轮次只负责自己的 `message_sequence`，必须通过 QQ 发送工具回复原目标。
- 分支可以并行完成；回答写回共享历史时会插入到对应请求之后，不以完成时间覆盖请求顺序。
- 分支启动 20 秒后仍未完成且尚未成功发送 QQ 消息时，辅助 LLM 根据该分支的历史
  快照生成一句自然、符合当前请求的进度回应，再由传输层发送；正常回复成功或分支结束
  都会取消生成和发送，进度回应本身不写入模型历史。生成失败时不使用固定模板兜底。

撤回指令在进入 LLM 前识别，例如“取消当前任务”“撤回刚才的任务”或 `/cancel`。
它会取消发令者最新的活动轮次；“取消全部任务”会同时取消该来源的所有活动轮次和后台
任务。确认消息仍通过原 QQ 发送工具发回，因此只能由已经通过 gate 的消息触发。

## 时序规则

- `message_sequence`：Core 为每条 TUI、QQ、定时器及后台整合输入分配的进程内单调序号。
- `task_sequence`：后台任务创建序号，独立于实际完成时间。
- 每个分支记录 `started_at` 和 `completed_at`，后台事件同时记录创建、完成和整合时间。
- 后创建任务可以先完成，但必须在较早任务整合后才能进入共享历史。
- 多个分支在任务内部并发执行，汇总结果保持工具参数中的声明顺序。
- 普通分支和后台整合都重新获取共享 `turn_lock` 写历史；模型和工具调用不持有该锁。

这套规则保证模型同时看到“请求何时到达”和“后台结果何时完成”，不会把完成顺序
误当成请求顺序。

## 投递目标

每个分支必须解析为一个明确目标：

| kind | 目标字段 | 投递工具 |
|---|---|---|
| `origin` | 从创建任务的会话推导 | 按来源选择下列工具 |
| `backend` | TUI session ID | `send_backend_message` |
| `qq_private` | QQ 用户号 | `send_private_msg` |
| `qq_group` | QQ 群号 | `send_group_msg` |

同一并行任务不允许重复目标。整合循环记录已成功投递的目标，错误目标、重复发送和
直接回答替代工具发送都会被拒绝；所有目标成功后才允许结束该整合轮次。

## 可观察性

TUI 分别展示任务已挂起、分支完成和按序整合三个事件。日志包含 `task_id`、
`task_sequence`、session、毫秒时间和耗时。普通入站日志还包含平台原始时间、
Core 接收时间、接收延迟及 `message_sequence`。

后台任务状态当前保存在内存中，Core 重启会取消尚未完成的任务；对话历史仍由
`echo-sessions.json` 正常持久化。
