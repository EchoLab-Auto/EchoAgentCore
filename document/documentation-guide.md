# 文档规范

> **定位**：本目录（`document/`）是一个 ProDoc 文档群。本文规定**文档该怎么分层、每层怎么写**——写任何文档前先读本文。读者：维护本仓库文档的开发者（含 Agent）。
> 框架语法（参数区、link 连线、悬停分块、坐标）属 ProDoc 渲染器规范，见 ProDoc 仓库的《规则定义》；本文只管**内容与结构约定**。

## 文档分层（从框架到细节）

文档群按"读者离框架的距离"分四层，画布上的连线深度与之对应：

| 层 | 回答的问题 | 代表文档 |
|---|---|---|
| 总览层 | 这是什么、从哪读起 | `index`、`architecture` |
| 框架层 | 系统如何组成与运转（机制、不变量、边界） | `core`、`frame`、`plugins` |
| 子系统层 | 某个能力如何设计与实现 | `agents`、`tools`、`panel-*` |
| 细节/操作层 | 怎么用、怎么运维、精确参考 | `protocol`、`ops-deploy`、`dev-testing` |

写作口吻按层区分：总览层 = 导航 + 要点；框架层 = 机制与边界（**不写实现细节**）；子系统层 = 设计 → 机制 → 细节；细节层 = 面向操作与查询，密度可以高。

**关键纪律：细节不向上渗漏。** 总览/框架层文档里不出现实现细节（具体函数、行号、单点修复）；细节层文档里不重复机制原理（引用框架层即可）。

## 目录分层与放置规则

物理目录把**长期参考类**（模块文档、操作手册）与**设计过程类**（计划 / 提案 / 设计记录）分开；画布 `group` 为既有分组名（渲染器视角），与目录对应如下：

| 目录 | 内容 | 画布 group |
|---|---|---|
| 根目录 | `index`（入口）、`documentation-guide`（本规范） | 总览 / 工程 |
| `overview/` | 架构总览与骨架 | 总览 |
| `core/` | 内核与运行时子系统（`frame`、`core-*`、`security-redaction-design`） | 框架 |
| `plugins/` | 插件体系、各插件与插件实例、插件开发指南 | 插件 |
| `federation/` | 联邦（多机去中心化） | 插件 |
| `protocol/` | 前后端线协议 | 工程 |
| `panel/` | Panel 前端与各视图契约 | 前端 |
| `ops/` | 部署与运维 | 工程 |
| `dev/` | 开发与测试规范 | 工程 |
| `design/` | 计划、提案与设计记录（含已实施记录，首段标注状态） | 规划 |

放置规则：新增文档先选目录——长期参考写进对应主题目录，计划/提案/记录进 `design/`；调研、审计等过程材料放 `source/research/`，不进本文档群。目录内文档引用其他目录用相对路径（`../xxx/`）。

## 单篇体例（五条）

1. **定位段**：H1 之后紧接一段引用块——覆盖什么、读者是谁、与哪些文档相关
2. **篇内分层序**：概念模型 → 机制 → 参考细节；结论/定位先行，细节收尾
3. **H2 = 可导航名词**：每篇 2-6 条为宜（画布悬停面板最多展示 6 条分块）；**不出现日期、议题号、阶段编号**（如「多实例」「议题 5」「P3-1」）
4. **日期退场**：行为性变更写成正常表述（「门控支持多实例」），不标注日期；纯过程史由 git 承担，不写进正文
5. **链接分两类**：正文相对链接（`./xxx.md`）表达任意引用；**画布连线（参数区 `link`）只放主干导航**（通常就是本文档的直接子文档）——交叉引用不进参数区，避免拖乱画布层级

### 四种文档类型的结构模板

#### 总览 / 入口（index、core、panel、dev-guide）

定位段 → 系统结构一览（图或清单）→ 阅读路径 → 延伸链接。短小，只做导航与导语。

#### 框架 / 机制（frame、plugins、agents、memory）

定位段 → 概念模型（原则、术语、边界）→ 机制（运作方式、生命周期）→ 参考（表格）。不写具体实现位置。

#### 子系统 / 设计（tools、skills、qq-gating、federation、panel-*）

定位段 → 设计目标 → 运作机制（管道 / 生命周期 / 数据流）→ 细节参考 → 关键决策与边界。历史注记以"现状句 + 必要时一句沿革"消化，不设变更日志节。

#### 细节 / 操作 / 参考（protocol、ops-deploy、dev-testing）

定位段 → 按功能域分节（传输 / 命令 / 事件；安装 / 更新 / 回滚…）。表格优先，步骤可密集。

### 检查清单

- [ ] 有定位段（读者、范围、相关文档）
- [ ] 位于正确分层目录；跨目录引用用相对路径且无断链
- [ ] H2 数量 2-6 条，标题是名词、无日期/编号污染
- [ ] 概念在前、细节在后；无跨层内容渗漏
- [ ] 行为性变更未标注日期；无纯过程史段落
- [ ] 正文相对链接有效
- [ ] 参数区 `link` 只含主干导航（= 直接子文档），与正文导航一致；**不出现多父**（一个框只被一条 `link` 指向）
- [ ] **引用代码用「文件 + 符号名」，不写行号**（见下）

## 文档图与 ProDoc 约定

### 参数区与 link 语义（速查）

- **参数区**（frontmatter）：`id` / `title` / `x` / `y` / `group` / `link`；坐标由画布拖拽或按同组网格手改
- **link 条目**支持 `目标 | 标签 | 源边>目标边`（`t/r/b/l`，`_` 为自动）；标签与连接边可在画布图编辑模式可视化修改
- **悬停分块** = 正文 H2；命名即导航，善用（2–6 条为宜：面板最多展示 6 条，超出折叠为 `+N`）
- 新增文档：补参数区 → 放入对应分层目录 → 从父文档 `link` 挂入 → 坐标与本组网格对齐 → 正文用本规范模板

### link：只放主干，且与 flow 一致

`index.md` 的「导航地图」flow 是**主干的权威定义**；画布参数区必须与它一致，否则正文与图各说一套。

- **link = 主干导航**（父 → 它的直接子文档）。交叉引用一律走正文相对链接，不进参数区
- 判据不是「物理目录」，而是 **`index.md` flow 里的父子边**：`core → plugins`、`plugins → federation`、`dev-guide → documentation-guide` 这类跨目录边是合法的（逻辑层级 ≠ 目录层级）；反过来，同目录兄弟互链（`panel-desktop-layout → panel-chat`）不合法
- 新增一条 link 前先看 flow：flow 里没有这条边，就不要加
- 子节点是否互链：**由该层的入口文档统一导航**，子节点之间不互链（避免画布上出现横七竖八的兄弟边）

### 坐标：一组一带，组内网格

| 规则 | 取值 | 理由 |
| --- | --- | --- |
| 组间纵向分区 | 每组独占一条横带，相邻带留 ≥ 120px | 组区域 = 成员包围盒 + padding（左右/下 24、顶部 34），留够才不会互相压 |
| 组内 x 步距 | **320** | 框宽 220 + 88 间隙；横滚与标签都不打架 |
| 组内 y 层距 | **160**（同层）/ **280**（跨层） | 同层并列用 160；父子分层用 280，给连接边留弧顶 |
| 父节点位置 | 子节点群的**正上方居中** | auto 选边会得到「向下扇形」，不横向扫过同排框 |
| 同排多子 | 从左到右按 fork 顺序 | 与正文清单顺序对齐，读者能靠位置记住 |

### 连接边：只在避障时显式写

缺省由 ProDoc 按两框主导方向自动选边，**大多数情况不用写**。只有一种情况要显式指定：

- 自动选出的边会让贝塞尔曲线**穿过第三个框** → 用 `| 源边>目标边` 换一条出/入边绕开

判断方法：按两框中心算，`|Δy| ≥ |Δx|` 走上下、否则走左右；若这条曲线在途中扫到别的框，就换边。极端情况（根到远端组的长边）无解——52 框单图必然有 1–2 条结构性长边跨过中间组，属预期，不必为它挪乱整张图。

### 画布自检（改完坐标后跑一遍）

`echo-prodoc check` 只查断链/环/孤立/缺参数区，**不查框重叠与连线穿框**。三项人工核对：

1. 同组内任意两框 `|Δx| ≥ 220 || |Δy| ≥ 96`（否则重叠）
2. 组区域两两不交（含 padding）
3. 每条连线：端点取边中点、控制点沿法线，采样曲线不落入第三方框

## 引用代码的写法

跨仓库文档与代码不在同一提交里演进，**行号是不可维护的锚点**：对 Panel 组
10 篇文档抽样 19 条 `文件:行号` 引用，15 条已漂移（79%）。行号失效时读者仍能找到
文件，却定位到无关代码——比不写行号更有害。

- ✅ `connection.ts` 的 `nextRetryMs`、`ChatView.vue` 的 `leftRailVisible`、`rail-cards.ts::railRegistered`
- ❌ `connection.ts:262`、`ChatView.vue:280`
- 需要范围时写函数/段落名：`SettingsView.vue` 的 `categories` computed、`proxy.rs` 的 `broadcast` 分支
- 例外：**行号本身是契约**的场合（如源码契约测试断言的 CSS 片段）可保留，但须写明「行号仅供定位，以符号名为准」

## 自动生成的文件（不要手改）

少数文档的内容是**从代码生成的**，手改会在下一次门禁被覆盖或判红：

| 文件 | 生成源 | 刷新 |
| --- | --- | --- |
| `plugins/tool-catalog.md` | `echo-agent::tool::builtin::register_all` 的真实注册表 | `UPDATE_DOCS=1 cargo test -p echo-agent-core --test doc_catalog` |

约定：

- 文件首行带 `<!-- 自动生成，请勿手改：<源> -->` 注释——看到它就改代码后重跑生成；
- 门禁在 `source/core/tests/doc_catalog.rs`：**工具目录新鲜度** + **内置插件 id 不许漏**（`BUILTIN_PLUGIN_IDS` 每项必须出现在 `core-plugins.md`）+ **相对链接可达**（`document/` 全树死链检查）；
- 生成只覆盖整份文件：想写人工说明就写进相邻的散文文档（如 `core-tools.md`），不要在生成文件里加章节。

## 自检与预览

改完文档先跑**图校验**，再看画布——校验能抓出断链、环、孤立框与缺参数区，画布只告诉你「不好看」：

```bash
# 校验（断链 / 环 / 孤立文档 / 缺参数区；CI 可加 --no-fail-on-warn 只报告）
echo-prodoc check ./document

# 本机预览
echo-prodoc view ./document

# 开放给同网段的其他设备（手机 / 另一台机器看画布）
echo-prodoc view ./document --host 0.0.0.0 --port 3344 --no-open
```

- **孤立框**是最常见的结构问题：新增文档忘了从父文档 `link` 挂入，它就在画布上漂浮。`check` 会点名，按提示补一条 `link` 即可
- **`--persist-layout`** 只控制「自动布局坐标是否写回参数区」；**查看器本身就能改源文件**——内置编辑器的保存/删除走 `/__prodoc_api/save`、`/__prodoc_api/delete`，与这个参数无关。所以 `--host 0.0.0.0` 之后同网段的设备**能直接改你的 .md**（这些接口无鉴权），只在自己信任的网络里这么开
- 长期在线的预览服务用 `systemd-run --user --collect --unit=<名称>` 起，别用 `nohup`——Core 重启或会话结束时不会被连带清理，`systemctl --user stop <名称>` 收掉
