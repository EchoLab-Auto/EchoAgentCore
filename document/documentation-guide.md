# 文档规范

> **定位**：本目录（`document/`）是一个 ProDoc 文档群。本文规定**文档该怎么分层、每层怎么写**——写任何文档前先读本文。读者：维护本仓库文档的开发者（含 Agent）。
> 框架语法（参数区、link 连线、悬停分块、坐标）属 ProDoc 渲染器规范，见 ProDoc 仓库的《规则定义》；本文只管**内容与结构约定**。

## 文档分层（从机制到细节）

文档群按"读者离实现的距离"分四层，画布上的连线深度与之对应（四层是**阅读距离**，不是画布分组——后者见下一节）：

| 层 | 回答的问题 | 代表文档 |
|---|---|---|
| 总览层 | 这是什么、从哪读起 | `index`、`architecture` |
| 机制层 | 系统如何组成与运转（机制、不变量、边界） | `core`、`frame`、`modules` |
| 子系统层 | 某个能力如何设计与实现 | `agents`、`tools`、`chat`、`settings-*` |
| 细节/操作层 | 怎么用、怎么运维、精确参考 | `protocol`、`deploy`、`testing` |

写作口吻按层区分：总览层 = 导航 + 要点；机制层 = 机制与边界（**不写实现细节**）；子系统层 = 设计 → 机制 → 细节；细节层 = 面向操作与查询，密度可以高。

**关键纪律：细节不向上渗漏。** 总览/机制层文档里不出现实现细节（具体函数、行号、单点修复）；细节层文档里不重复机制原理（引用机制层即可）。

## 目录分层与放置规则

物理目录按**主题 × 阅读距离**分层；画布 `group` 只有四个——`总览` / `Core` / `前端` / `工程`，与目录对应如下：

| 目录 | 内容 | 画布 group |
|---|---|---|
| 根目录 | `index`（入口）、`documentation-guide`（本规范） | 总览 / 工程 |
| `overview/` | 架构总览与骨架 | 总览 |
| `core/` | 内核与运行时子系统（`frame`、`agent-loop`、`agents`、`memory`、`multimodal`、`config-persistence`、`logging`、`security-redaction`） | Core |
| `modules/` | 模块体系入口 + **每个模块一篇**（一模块一文档）+ 模块开发指南 | Core |
| `federation/` | 联邦（多机去中心化）——它是 `echo-agent.federation` 模块的文档，按主题独立成目录 | Core |
| `protocol/` | 前后端线协议 | 工程 |
| `panel/` | Panel 前端与各视图契约 | 前端 |
| `ops/` | 部署与运维 | 工程 |
| `dev/` | 开发与测试规范 | 工程 |

**为什么 `core/` 与 `modules/` 同属一个组**：框架本身就是模块化设计的——`core` 由「框架（内核）」与「模块化设计」两支组成（见 [Core 后端](./core/core.md)「Core 的组成」）。把二者拆成两个并列的顶层分组，等于在画布上宣称"框架不是模块化的、模块是框架之外的东西"，与实现相反。画布上它们仍是 Core 组内的两条分支列（内核列 / 模块列，中间留一列空位），层级关系由 `core → frame → 子系统`、`core → modules → 各模块` 两张连线网表达。

**模块树是一比一的**：`modules.md` 的表格必须逐项覆盖 `BUILTIN_MODULE_IDS` 的全部 22 项 + 实例模块 `echo-agent.instance.qq`，且每项都带一个**可达的文档链接**。判据不是「值不值得写一篇」，而是「模块树要能被逐项核对」——一个 id 在表里但没有树节点，读者就无法从那棵树走到它的契约；反过来，画布上多出一个不对应任何模块的节点，说明它在清单里没有位置。

唯一的合并是 `kernel`：9 个 `kind = kernel` 模块（`defs` / `config` / `protocol` / `session` / `tool` / `shell` / `federation` / `sanitize` / `loop`）共用 [运行地基](./modules/kernel.md) 一篇。它们的分界判据完全一致（都是"别人的运行地基"、都禁不掉），逐篇会得到 9 份几乎相同的「纯身份声明」——合并成一篇讲共性，逐个职责用一张表列。**其余 14 项一 id 一篇**。

### 三条结构不变量（`tools/prodoc_layout.py` 装配期即拦）

画布 `link` 是**导航**，不是引用。三条判据按"读者能不能顺着树走"定，违反时脚本直接 `exit 2` 并点名：

| 不变量 | 违反后果 | 报错样例 |
|---|---|---|
| **无环** | 渲染器把环上成员缩进同一个强连通分量、排在同一层，父子关系在画布上消失 | `检测到循环连线：a → b → c → a` |
| **无多父** | 同一个框被两条 `link` 指向，它有两个"上家"，树不再是树 | `doc b 有多个父节点（a / c）` |
| **无孤立根** | `index` 之外的框没有入边，就漂在画布上，读者从入口走不到它 | （由"根 = index 唯一"的布局规则暴露） |

最常见的违反方式是**写背链**：在子文档里写下指回父文档的 `link`（`sanitize → modules`）。这不是"补一条反向导航"，而是把父文档变成子文档的子节点。**要表达「相关」就走正文相对链接**，参数区留空。

每篇模块文档的**必答四问**（各占一节，节名可变，2–6 条 H2 的约束不变）：

| 必答 | 内容 |
|---|---|
| **身份与贡献** | id / kind / 名称与路由 / 贡献了什么（服务键、命令域、工具、服务依赖） |
| **宿主接缝** | `inject` 声明什么、`mount` 绑什么、谁解析它、缺了会怎样 |
| **启停与门控** | persona 白名单还属进程级、有没有自锁、全局关掉的实际效果 |
| **边界** | 它不做什么，以及对应的机制细节去哪篇读 |

外加一节「**为什么是独立模块**」——它与相邻模块的分界判据。**这一节不是锦上添花**：一个模块说不清"为什么不能并进别人"，通常说明它还不该独立。

**机制原理不写进模块文档**——那属于对应子系统（Shell 的进程组生命周期在 `modules/tools.md`，压缩算法在 `core/agent-loop.md`，脱敏算法在 `core/security-redaction.md`），模块文档只回答「这个可插拔单位长什么样」。例外是**该机制只在这里写过**（`skills` / `subagent` / `qq-gating` 三篇同时承担机制文档），此时按机制文档的体例写，四问仍须覆盖。

`group` 与「四层」（总览 / 机制 / 子系统 / 细节）**不是一回事**：四层是**阅读距离**（决定写作口吻与细节密度），`group` 是**画布分区**（决定位置）。一篇「机制层」文档可以落在 `Core` 组，也可以落在 `工程` 组。

### 文件命名

目录已经表达的主题，文件名里不重复——`panel/` 下不叫 `panel-chat`，`core/` 下不叫 `core-memory`，`ops/` 下不叫 `ops-deploy`。

| 规则 | 示例 |
|---|---|
| 入口页与目录同名 | `core/core.md`、`panel/panel.md`、`modules/modules.md` |
| 文件名 = 目录内语义名，语义前缀保留、目录前缀去掉 | `panel/chat-list.md`、`panel/settings-tools.md`、`core/agent-loop.md`、`ops/deploy.md` |
| 模块文档按模块短名命名（去掉公共前缀 `echo-agent.`） | `echo-agent.shell` → `modules/shell.md`、`echo-agent.provider.llm` → `modules/provider-llm.md` |
| `id` 恒等于文件名（不含 `.md`），全群唯一 | `chat-list`、`agent-loop`、`deploy` |

`id` 与文件名绑定后，**改文件名 = 改 id**：`link` 连线与正文相对链接都要同步改（画布坐标、`group` 不受影响）。门禁见下方检查清单。

## 单篇体例（五条）

1. **定位段**：H1 之后紧接一段引用块——覆盖什么、读者是谁、与哪些文档相关
2. **篇内分层序**：概念模型 → 机制 → 参考细节；结论/定位先行，细节收尾
3. **H2 = 可导航名词**：每篇 2-6 条为宜（画布悬停面板最多展示 6 条分块）；**不出现日期、议题号、阶段编号**（如「多实例」「议题 5」「P3-1」）
4. **日期退场**：行为性变更写成正常表述（「门控支持多实例」），不标注日期；纯过程史由 git 承担，不写进正文
5. **链接分两类**：正文相对链接（`./xxx.md`）表达任意引用；**画布连线（参数区 `link`）只放主干导航**（通常就是本文档的直接子文档）——交叉引用不进参数区，避免拖乱画布层级

### 四种文档类型的结构模板

#### 总览 / 入口（index、core、panel、guide）

定位段 → 系统结构一览（图或清单）→ 阅读路径 → 延伸链接。短小，只做导航与导语。

#### 框架 / 机制（frame、modules、agents、memory）

定位段 → 概念模型（原则、术语、边界）→ 机制（运作方式、生命周期）→ 参考（表格）。不写具体实现位置。

#### 子系统 / 设计（tools、skills、qq-gating、federation、chat-*）

定位段 → 设计目标 → 运作机制（管道 / 生命周期 / 数据流）→ 细节参考 → 关键决策与边界。历史注记以"现状句 + 必要时一句沿革"消化，不设变更日志节。

#### 细节 / 操作 / 参考（protocol、deploy、testing）

定位段 → 按功能域分节（传输 / 命令 / 事件；安装 / 更新 / 回滚…）。表格优先，步骤可密集。

### 检查清单

- [ ] 有定位段（读者、范围、相关文档）
- [ ] 位于正确分层目录；文件名不带目录前缀；`id` == 文件名；跨目录引用用相对路径且无断链
- [ ] H2 数量 2-6 条，标题是名词、无日期/编号污染
- [ ] 概念在前、细节在后；无跨层内容渗漏
- [ ] 行为性变更未标注日期；无纯过程史段落
- [ ] 正文相对链接有效
- [ ] 参数区 `link` 只含主干导航（= 直接子文档），与正文导航一致；**不出现多父**（一个框只被一条 `link` 指向）
- [ ] **引用代码用「文件 + 符号名」，不写行号**（见下）

## 文档图与 ProDoc 约定

### 参数区与 link 语义（速查）

- **参数区**（frontmatter）：`id` / `title` / `x` / `y` / `group` / `link`；坐标由画布拖拽或按同组网格手改
- **link 条目**支持 `目标 | 标签 | 源边>目标边`（`t/r/b/l`，`_` 为自动）；标签与连接边可在画布图编辑模式可视化修改
- **悬停分块** = 正文 H2；命名即导航，善用（2–6 条为宜：面板最多展示 6 条，超出折叠为 `+N`）
- 新增文档：补参数区 → 放入对应分层目录 → 从父文档 `link` 挂入 → 坐标与本组网格对齐 → 正文用本规范模板

### link：只放主干，且与 flow 一致

`index.md` 的「导航地图」flow 是**主干的权威定义**；画布参数区必须与它一致，否则正文与图各说一套。

- **link = 主干导航**（父 → 它的直接子文档）。交叉引用一律走正文相对链接，不进参数区
- 判据不是「物理目录」，而是 **`index.md` flow 里的父子边**：`core → modules`、`modules → federation`、`guide → documentation-guide` 这类跨目录边是合法的（逻辑层级 ≠ 目录层级）；反过来，同目录兄弟互链（`desktop-layout → chat`）不合法
- 新增一条 link 前先看 flow：flow 里没有这条边，就不要加
- 子节点是否互链：**由该层的入口文档统一导航**，子节点之间不互链（避免画布上出现横七竖八的兄弟边）

### 坐标：一组一带，组内网格

本节规则由 **`tools/prodoc_layout.py`** 实现——它是唯一实现，本文只写理由。要重排就跑：

```bash
python3 tools/prodoc_layout.py                   # 先看排布表（不改文件）
python3 tools/prodoc_layout.py --write           # 落盘（只改 x / y / link 三行）
python3 tools/prodoc_layout.py --write --verify   # 落盘并按真实渲染几何自检
```

组带自上而下：`总览 → Core → 前端 → 工程`（总览在最上做入口，前置于后端，工程收在末尾）。

| 规则 | 取值 | 理由 |
| --- | --- | --- |
| 组间纵向分区 | 每组独占一条横带，相邻带留 ≥ 120px | 组区域 = 成员包围盒 + padding（左右/下 24、顶部 34），留够才不会互相压 |
| 组内 x 步距 | **320** | 框宽 220 + 88 间隙；横滚与标签都不打架 |
| 组内 y 层距 | **160**（同层）/ **280**（跨层） | 同层并列用 160；父子分层用 280，给连接边留弧顶 |
| 同排多子 | 从左到右按 fork 顺序 | 与正文清单顺序对齐，读者能靠位置记住 |
| 组根位置 | 贴本组**左边界**（`x = 960`），左侧留出 `index` 扇出通道 | 组根是跨组边的落点；只有它的左边界固定，长边才能走空通道而不穿框 |
| 父节点对齐 | `Core` **左对齐**（贴子群最左）；`前端` **居中**（落子群正中） | Core 是双主干（内核列 / 模块列），左对齐让主干连成一条竖线；前端是多叉树，居中避免长斜边 |

三个例外是设计出来的，不是随手摆的：

- `index` 独占左上角（`x = 160`），六条出边统一从**右边界**离开（`r>l`），沿通道下行后各自进组根；`architecture` 在它正下方
- `Core` 的两条分支列之间**空一整列**（内核列 `960..2560`，模块列 `3200..4800`）——留出间隔，"两支同属 Core"才看得出来；不留空位时 12 个框连成一排，读者只能靠连线猜分组
- `工程` 组的三个根（`protocol` / `deploy` / `guide`）**同层竖排**在同一列（`x = 960`，`y` 步距 160）——它们都要落在通道右边界上，否则根到远端组的长边会横穿中间组带

### 连接边：只在避障时显式写

缺省由 ProDoc 按两框主导方向自动选边，**大多数情况不用写**：行间距 280 远大于框高 96，父在上子在下必然得到「底出顶进」。

要显式指定只有一种情况：自动选出的边会让贝塞尔曲线**穿过第三个框**——用 `| 源边>目标边` 换一条出/入边绕开。本图里只有六条边需要：

| 边 | 写法 | 为什么 |
| --- | --- | --- |
| `index → core / panel / protocol / deploy / guide` | `r>l` | 从 `index` 右边界出发、沿左侧通道下行，进组根左边界；通道内无框，曲线不可能穿框 |
| `core → modules` | `b>t` | `frame` 与 `modules` 同层、同在 `core` 之下；`b>t` 让两支并列成扇形，而自动选边会判成左右相接，让 `frame` 被绕过 |

判断方法：按两框中心算，`|Δy| ≥ |Δx|` 走上下、否则走左右；若这条曲线在途中扫到别的框，就换边。**能靠通道解决的，不要靠挪框解决**——一旦为某条边挪动组带，全部组的对齐都跟着散。

### 画布自检（改完坐标后跑一遍）

`echo-prodoc check` 只查断链 / 环 / 孤立 / 缺参数区，**不查框重叠与连线穿框**。后四项交给仓库里的脚本：

```bash
python3 tools/prodoc_layout.py --verify          # 校验「按规则重排后」是否干净
python3 tools/prodoc_layout.py --verify --from-disk   # 校验磁盘上的现有坐标
```

四项检查：框重叠、组区域相交、连线穿框、边贴线（两条边长时间重合、视觉上分不清谁连谁）。几何一律取自 DocRenderer 的 `prodoc-core` 源码——贝塞尔路由、分层布局的长边拐点、组区域 padding 都用它的真实实现，脚本里没有第二份算法。所以脚本需要一份 [DocRenderer](https://github.com/EchoLab-Auto/DocRenderer) 检出（`--docrenderer` 或 `PRODOC_RENDERER` 环境变量指定）；找不到就**直接失败**而不降级——复写一份路由算法必然与渲染器漂移，那样的「通过」比不校验更有害。

## 写作细则：代码引用与生成文件

### 引用代码

跨仓库文档与代码不在同一提交里演进，**行号是不可维护的锚点**：对 Panel 组
10 篇文档抽样 19 条 `文件:行号` 引用，15 条已漂移（79%）。行号失效时读者仍能找到
文件，却定位到无关代码——比不写行号更有害。

- ✅ `connection.ts` 的 `nextRetryMs`、`ChatView.vue` 的 `leftRailVisible`、`rail-cards.ts::railRegistered`
- ❌ `connection.ts:262`、`ChatView.vue:280`
- 需要范围时写函数/段落名：`SettingsView.vue` 的 `categories` computed、`proxy.rs` 的 `broadcast` 分支
- 例外：**行号本身是契约**的场合（如源码契约测试断言的 CSS 片段）可保留，但须写明「行号仅供定位，以符号名为准」

### 自动生成的文件

少数文档的内容是**从代码生成的**，手改会在下一次门禁被覆盖或判红：

| 文件 | 生成源 | 刷新 |
| --- | --- | --- |
| `modules/tool-catalog.md` | `echo-agent::tool::builtin::build_registry` 的真实注册表 | `UPDATE_DOCS=1 cargo test -p echo-agent-core --test doc_catalog` |

约定：

- 文件首行带 `<!-- 自动生成，请勿手改：<源> -->` 注释——看到它就改代码后重跑生成；
- 门禁在 `source/modules/core/tests/doc_catalog.rs`：**工具目录新鲜度** + **内置模块 id 不许漏**（`BUILTIN_MODULE_IDS` 每项必须出现在 `modules.md`）+ **相对链接可达**（`document/` 全树死链检查）；
- 生成只覆盖整份文件：想写人工说明就写进相邻的散文文档（如 `tools.md`），不要在生成文件里加章节。

## 自检与预览

改完文档先跑**图校验**，再看画布——校验能抓出断链、环、孤立框与缺参数区，画布只告诉你「不好看」：

```bash
# 结构校验（断链 / 环 / 孤立文档 / 缺参数区；CI 可加 --no-fail-on-warn 只报告）
echo-prodoc check ./document

# 几何自检（框重叠 / 组区域相交 / 连线穿框 / 边贴线）
python3 tools/prodoc_layout.py --verify

# 重排坐标（规则见「坐标：一组一带，组内网格」）
python3 tools/prodoc_layout.py --write --verify

# 本机预览
echo-prodoc view ./document

# 开放给同网段的其他设备（手机 / 另一台机器看画布）
echo-prodoc view ./document --host 0.0.0.0 --port 3344 --no-open
```

- **孤立框**是最常见的结构问题：新增文档忘了从父文档 `link` 挂入，它就在画布上漂浮。`check` 会点名，按提示补一条 `link` 即可
- **`--persist-layout`** 只控制「自动布局坐标是否写回参数区」；**查看器本身就能改源文件**——内置编辑器的保存/删除走 `/__prodoc_api/save`、`/__prodoc_api/delete`，与这个参数无关。所以 `--host 0.0.0.0` 之后同网段的设备**能直接改你的 .md**（这些接口无鉴权），只在自己信任的网络里这么开
- 长期在线的预览服务用 `systemd-run --user --collect --unit=<名称>` 起，别用 `nohup`——Core 重启或会话结束时不会被连带清理，`systemctl --user stop <名称>` 收掉
